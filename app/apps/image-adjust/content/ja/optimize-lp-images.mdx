ランディングページ（LP）は、広告やSNSから来た訪問者が最初に目にするページです。表示が遅いと、内容を読む前に離脱されてしまいます。そして LP の表示を遅くする最大の原因は、たいてい画像です。この記事では、画像を軽くしつつ見た目を保つための具体的な手順を、サイズ、形式、読み込み方、確認方法の順に整理します。

## まず適切なサイズを決める

画像を軽くする最も効果的な方法は、必要以上に大きな画像を使わないことです。4000px 幅のカメラ原本をそのまま載せ、CSS で小さく表示していると、見えない画素のぶんだけ無駄にダウンロードさせることになります。

### 推奨サイズの目安

ヒーロー画像（ページ最上部の大きな画像）は、幅 1920px 前後が一つの目安です。これでフル HD のディスプレイで全幅表示しても足ります。それより大きく表示する場面は多くありません。本文中の画像は、表示される幅の 2 倍程度までで十分なことが多いです。

### 高解像度ディスプレイの考え方

スマートフォンや一部のノートパソコンは、1 CSS ピクセルを 2×2 以上の物理ピクセルで描画します（デバイスピクセル比 2 など）。そのため、表示幅が 400 CSS ピクセルの画像を綺麗に見せるには、幅 800px の画像が必要になります。ただし、3 倍、4 倍と増やしても見た目の差は小さく、ファイルだけが重くなります。実用上は 2 倍までを目安にし、それ以上は無理に用意しないのが現実的です。

画面の幅によって必要なサイズが違うので、1 枚の巨大な画像を全員に配信するのではなく、複数のサイズを用意して出し分けます（後述の `srcset`）。

## 形式を選ぶ

形式の選び方の詳細は [画像形式の選び方](/guide/image-formats/) にまとめています。LP 向けの要点は次のとおりです。

- 写真：WebP（非可逆）か JPEG。WebP のほうが小さくなりやすく、現行の主要ブラウザすべてが対応しています（Safari は 14 以降）。
- ロゴ・アイコン：SVG。なければ PNG か可逆 WebP。
- 透過が必要な画像：PNG か WebP。
- スクリーンショット：文字が多ければ PNG か可逆 WebP。
- アニメーション：長いものは GIF を避け、動画（MP4・WebM）か WebP アニメーションを検討する。

変換は、本サイトの [PNG から WebP](/convert/png-to-webp/)、[JPEG から WebP](/convert/jpeg-to-webp/)、[PNG から JPEG](/convert/png-to-jpeg/) などのツールで行えます。複数の画像をまとめて処理することもできます。

## 品質の目安と目標サイズ

非可逆形式（JPEG・WebP）では、品質の数値を下げるほどファイルが小さくなります。数値の意味はエンコーダによって異なりますが、おおよその出発点は次のとおりです（あくまで目安です）。

| 用途 | 品質の目安 | 目標ファイルサイズの目安 |
| --- | --- | --- |
| ヒーロー画像（全幅） | 75〜85 | 200〜300KB 以下 |
| 本文中の写真 | 70〜80 | 100KB 前後以下 |
| サムネイル・カード画像 | 65〜75 | 30〜50KB 以下 |
| ロゴ・アイコン（SVG） | 該当なし | 数 KB 程度 |

この数値は絶対的な基準ではありません。画像の内容（細かい模様が多いか、ベタ塗りが多いか）で、同じ品質でもサイズは大きく変わります。品質を一段ずつ下げて、劣化が目立ち始める直前で止めるのが基本です。

本サイトの [圧縮ツール](/) は、品質を数値で指定する方法のほか、目標のファイルサイズを指定する方法も選べます。「ヒーロー画像は 300KB 以内にしたい」といった場面で便利です。形式別には [JPEG の圧縮](/compress/jpeg/)、[PNG の圧縮](/compress/png/)、[WebP の圧縮](/compress/webp/)、[GIF の圧縮](/compress/gif/) があります。

## srcset と sizes で画面に合った画像を配信する

ブラウザに複数サイズの候補を渡し、画面幅に合う画像を選ばせる仕組みが `srcset` と `sizes` です。

```html
<img
  src="hero-1200.jpg"
  srcset="hero-640.jpg 640w, hero-1200.jpg 1200w, hero-1920.jpg 1920w"
  sizes="100vw"
  width="1920"
  height="1080"
  alt="商品を使うイメージ">
```

`srcset` の `640w` などは、その画像の実際の幅（ピクセル）です。`sizes` は、その画像が画面上で表示される幅を表します。`100vw` は画面幅いっぱいです。ブラウザはこの 2 つと、画面の解像度から、最適な候補を自動で選びます。本文の幅が決まっている画像なら、たとえば `sizes="(min-width: 800px) 720px, 100vw"` のように書きます。

## picture 要素で形式を出し分ける

`picture` 要素を使うと、WebP に対応しないブラウザには JPEG を渡す、といった出し分けができます。

```html
<picture>
  <source type="image/webp"
          srcset="hero-640.webp 640w, hero-1200.webp 1200w, hero-1920.webp 1920w"
          sizes="100vw">
  <img src="hero-1200.jpg"
       srcset="hero-640.jpg 640w, hero-1200.jpg 1200w, hero-1920.jpg 1920w"
       sizes="100vw"
       width="1920" height="1080"
       alt="商品を使うイメージ">
</picture>
```

現行の主要ブラウザは WebP に対応しているため、WebP だけにしても実害は少ないケースが多いです。古い環境を考慮する必要があるかどうかは、アクセス解析の傾向で判断してください。

## width と height で CLS を防ぐ

画像の読み込みが終わってからレイアウトがずれる現象は、累積レイアウトシフト（CLS）として計測され、体感の悪さにつながります。対策は簡単で、`img` に `width` と `height` 属性を付けるだけです。

```html
<img src="photo.webp" width="800" height="450" alt="説明">
```

ここで指定する値は、画像本来のピクセル数（アスペクト比がわかる数値）です。最近のブラウザは、この値から表示前に縦横比を確保します。幅を CSS で可変にする場合は、次のように書くと比率が保たれます。

```css
img {
  max-width: 100%;
  height: auto;
}
```

## loading="lazy" は画面外の画像だけ

`loading="lazy"` を付けると、画像がスクロールで近づくまで読み込みが遅延され、最初の通信量が減ります。

```html
<img src="case-study.webp" width="600" height="400" alt="事例" loading="lazy" decoding="async">
```

重要なのは、ファーストビュー（最初に画面に見える範囲）の画像には付けないことです。ヒーロー画像に付けると、読み込み開始が遅れて、かえって LCP が悪化します。LP では、ページ下部の事例、お客様の声、フッター付近の画像に付けるのが基本です。

`decoding="async"` は、画像のデコードを他の処理と並行させる指定です。メインの描画をブロックしにくくなるので、画面外の画像には付けておくと無難です。

## LCP 画像には fetchpriority="high"

LCP（最大コンテンツの描画）は、ページの主要コンテンツが表示されるまでの時間で、多くの LP ではヒーロー画像がその対象になります。この画像には `fetchpriority="high"` を付けて、読み込みの優先度を上げます。

```html
<img src="hero-1200.webp" width="1920" height="1080" alt="..."
     fetchpriority="high">
```

ヒーロー画像を CSS の背景として書いていると、ブラウザが見つけるのが遅れます。可能なら `img` 要素にするか、`link rel="preload"` で先読みしてください。複数の画像に `high` を付けると意味が薄れるので、本当に重要な 1 枚だけにします。

## EXIF などのメタデータを削除する

カメラやスマートフォンで撮った写真には、撮影日時、機種、向き、場合によっては位置情報が含まれます。公開用の画像では、プライバシーの観点からも、容量の観点からも、不要なメタデータは削除しましょう。

本サイトのツールは、EXIF などのメタデータを既定で削除します。ブラウザ内で処理するため、画像がサーバーに送られることはありません。向き情報が消えて写真が横倒しにならないよう、変換後の見た目は必ず確認してください。

## 背景画像と SVG の扱い

### CSS の背景画像

`background-image` で指定した画像は、`srcset` が使えません。複数サイズの出し分けには `image-set()` やメディアクエリを使います。また、HTML を解析するだけでは発見されないので、ファーストビューの重要な背景なら `preload` を検討します。装飾以外の意味を持つ画像（ヒーローの商品写真など）は、`alt` を付けられる `img` 要素にしたほうが、アクセシビリティと速度の両方で有利です。

### SVG の最適化

SVG は、書き出したままだと、エディタ固有のメタデータや不要な定義が含まれ、無駄に大きいことがあります。不要な要素を削ると、見た目は変わらないまま小さくなります。本サイトの [SVG の圧縮](/compress/svg/) からも行えます。

## 確認方法

最適化の効果は、実測で確認します。

- Lighthouse：Chrome の開発者ツールで実行でき、LCP・CLS、画像に関する改善提案が出ます。
- PageSpeed Insights：[https://pagespeed.web.dev/](https://pagespeed.web.dev/) で URL を入れると、実際のユーザーのデータ（取得できる場合）と、ラボ計測の両方が見られます。
- 開発者ツールの「ネットワーク」タブ：画像ごとの転送サイズと、読み込み開始の順序を確認できます。

LCP と CLS の基準や改善の考え方は、[web.dev の Core Web Vitals](https://web.dev/articles/vitals) が一次情報です。LCP の「良好」の目安は 2.5 秒以内、CLS は 0.1 以下とされています。

## チェックリスト

- 表示幅の 2 倍程度を超える大きな画像を使っていない
- ヒーロー画像は幅 1920px 前後までで、200〜300KB 以下を目安に圧縮した
- 写真は WebP か JPEG、ロゴは SVG にした
- すべての `img` に `width` と `height` を付けた
- ファーストビュー外の画像に `loading="lazy"` を付け、ファーストビューの画像には付けていない
- LCP の画像に `fetchpriority="high"` を付けた
- 必要に応じて `srcset` と `sizes`、`picture` を使った
- EXIF などのメタデータを削除した
- SVG を最適化した
- Lighthouse か PageSpeed Insights で LCP と CLS を確認した

## まとめ

LP の画像最適化は、まず「大きすぎるサイズを減らす」、次に「軽い形式と品質にする」、最後に「読み込み方を整える」の順で進めると効果的です。サイズ縮小と形式変換は [画像変換・圧縮ツール](/) でまとめて行えます。ファビコンなどサイト全体のアイコンを整えたいときは、[ファビコンの設置方法](/guide/favicon-setup/) も参考にしてください。
